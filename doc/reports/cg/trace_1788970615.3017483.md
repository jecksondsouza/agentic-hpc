## Agent Reasoning (per iteration)

### Iteration 1 — baseline analysis
- **Observed:** initial best run used 1 thread on a single CPU → 24.532 s, 2449.51 Mop/s. Large headroom.
- **Hypothesis:** 8 physical cores with SMT; CG is memory-bandwidth-bound (spmv), so it should scale well across cores, but SMT siblings would add cache/bandwidth contention. Start with one thread per physical core.
- **Action:** `run_experiment(cpus=[0–7], num_threads=8)` — pinned to the primary threads.

### Iteration 2 — SMT scaling + underutilization check
- **Observed:** 4.859 s, 12394.37 Mop/s — ~5× speedup over 1 thread (not the ideal 8×); per-thread Mop/s dropped 2449.5 → 1549.3, indicating memory/L3 contention.
- **Hypothesis:** for a memory-bound workload, SMT siblings might fill memory stalls — test 16 threads. Also test 4 threads to bound the scaling curve from below.
- **Actions:** `run_experiment(cpus=[0–15], num_threads=16)` → 5.381 s, 10942.16 Mop/s; `run_experiment(cpus=[0–3], num_threads=4)` → 7.295 s, 8235.15 Mop/s.

### Iteration 3 — confirm the peak
- **Observed:** 16 threads (5.381 s) is *worse* than 8 threads (4.859 s) — negative scaling: SMT siblings compete for the shared 512 KB L2 and memory bandwidth. 4 threads (7.295 s) underutilizes the 8 cores.
- **Action:** `run_experiment(cpus=[0–5], num_threads=6)` → 5.351 s, 11231.42 Mop/s — confirms the curve peaks at 8, not 6.

### Iteration 4 — final analysis
- **Observed:** full scaling curve: 1→24.532 s, 4→7.295 s, 6→5.351 s, **8→4.859 s**, 16→5.381 s. Minimum is exactly at 8 threads.
- **Conclusion:** 8 threads on [0–7] is optimal. Binary, compile flags (`-O3 -fopenmp`), and problem size (Class B, N=75000) are fixed; thread count and CPU affinity were the only tunables and are now exhausted. Stopped.

## Reasoning Summary

**1. Thread count peaks at 8 (one per physical core).** The scaling curve is 1→24.532 s, 4→7.295 s, 6→5.351 s, **8→4.859 s**, 16→5.381 s. The minimum is exactly 8 threads: fewer underutilizes the 8 physical cores, more oversubscribes them via SMT.

**2. Scaling is sub-linear (5.05×, 63% parallel efficiency).** 1→8 threads gives only ~5× speedup because CG's inner loops (spmv, SAXPY, dot) are memory-bandwidth-bound and contend on the shared 96 MB L3 and memory path. Per-thread throughput falls monotonically (2449.5 → 1549.3 Mop/s) as threads are added.

**3. SMT hurts a bandwidth-bound kernel.** 16 threads (2/core) → 5.381 s is ~11% *slower* than 8 threads. SMT siblings share L1/L2, load/store units, and the memory path, so a second thread per core adds cache and bandwidth contention without adding effective memory bandwidth.

**4. Pinning to the primary threads [0–7] is the stable optimum.** 8 threads on the 8 primary (non-SMT) logical CPUs avoid SMT siblings entirely and yield 4.859 s / 12394.37 Mop/s — ~5.05× faster than the 1-thread baseline.
